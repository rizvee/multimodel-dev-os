# v4.2 Planning

v4.2 is planned as the next development cycle after the v4.1 Skill OS Foundation release. This document is a planning guide only; v4.2 is not shipped.

## 1. Current Release Baseline

- v4.1.0 is fully released on npmjs.
- GitHub release `v4.1.0` is public and latest.
- CI Verification and Deploy Docs are green.
- GitHub Packages publish workflow succeeded, but package visibility may still need manual GitHub settings review.
- v4.0.1 remains tagged and draft-released, but was never npm-published and is superseded by v4.1.0.
- `main` currently remains at package version `4.1.0`.

Recommended release-lane note: create a separate v4.2 dev-lane safety sprint before implementation if maintainers want `main` to move from `4.1.0` to a prerelease version such as `4.2.0-dev.0`.

## 2. What v4.1 Shipped

v4.1 shipped the Skill OS foundation:

- RACE+ prompt templates.
- Skill registry metadata.
- Prompt template registry metadata.
- Tool permission metadata.
- Agent cluster metadata.
- Declarative advisory guardrails.
- Workflow `skill_os` metadata references.
- Draft-only business operator templates.
- Read-only `skill-os` CLI inspection.
- Validation for bundled Skill OS registries and schemas.
- Migration, adoption, examples, and authoring documentation.

The v4.1 foundation remains validation-first. It does not execute automation, enforce permissions at runtime, call external tools, send messages, publish content, or make advisory guardrails block live commands.

## 3. Recommended v4.2 Direction

v4.2 should turn the v4.1 foundation into a more ergonomic, inspectable, and adoption-ready system without jumping directly to hidden enforcement or external writes.

Recommended direction:

- Improve read-only Skill OS CLI inspection before adding enforcement.
- Design opt-in guardrail enforcement before implementing it.
- Make workflow execution safety easier to understand through dry-run and planning output.
- Expand public, package-safe business operator examples without private connector assumptions.
- Align catalog/plugin metadata with Skill OS metadata.
- Harden release governance around skipped patch releases, post-release visibility, and release-lane state.

## 4. Non-Goals

v4.2 should not:

- Run external connectors automatically.
- Send emails, messages, calendar updates, CRM updates, or ad-spend changes.
- Publish packages, content, releases, DNS changes, or deployments without explicit confirmation.
- Enforce permissions silently.
- Break existing workflow YAML.
- Break existing markdown skills.
- Add runtime dependencies.
- Change the public npm package name.
- Treat v4.0.1 as an active release lane.

## 5. Proposed Sprint Sequence

### Sprint 0: v4.2 Development Lane Safety

Goal: decide whether `main` should move to a prerelease development version.

Recommended work:

- Keep this as a version-only and docs-only safety sprint if used.
- Consider `4.2.0-dev.0` only after explicit maintainer approval.
- Update release-state docs to make the v4.2 development lane explicit.
- Confirm v4.1.0 remains the npm latest before any version change.

### Sprint A: Skill OS CLI Inspection Improvements

Goal: make Skill OS metadata easier to inspect locally.

Possible work:

- Richer `skill-os show` output for skills, prompts, permissions, guardrails, workflows, and clusters.
- Registry filtering by category, risk level, permission class, or cluster.
- Validation summaries grouped by registry.
- Optional machine-readable JSON output if it matches existing CLI style.

Safety boundary:

- Read-only only.
- No registry mutation.
- No workflow execution changes.

### Sprint B: Guardrail Enforcement Design

Goal: design an advisory-to-enforced transition model before implementing enforcement.

Possible work:

- Define opt-in enforcement modes.
- Define confirmation requirements for write-capable and restricted operations.
- Define audit log shape for future enforcement.
- Document when a guardrail is advisory, warning-only, confirmation-required, or blocking.

Safety boundary:

- Design and docs first.
- No hidden blocking.
- No automatic external writes.

### Sprint C: Workflow Execution Safety Planning

Goal: improve workflow confidence without changing write behavior.

Possible work:

- Clearer dry-run output.
- Validation-before-run checks.
- Permission-aware workflow planning summaries.
- Explicit display of Skill OS metadata before workflow execution.

Safety boundary:

- No new external writes.
- No permission enforcement unless explicitly approved in a later sprint.
- Existing workflow commands remain backward-compatible.

### Sprint D: Business Operator Catalog Expansion

Goal: expand public, draft-only non-code workflow examples.

Possible work:

- Optional template packs for operator workflows.
- More sample outputs for safe draft-only work.
- Better examples for weekly review, KPI snapshot, content brief, SOP builder, and project pulse.
- Public/productized examples only.

Safety boundary:

- No private business data.
- No connector calls.
- No sending, publishing, spending, or external system updates.

### Sprint E: Plugin and Catalog Alignment

Goal: connect Skill OS metadata to catalog/plugin examples in a validation-only way.

Possible work:

- Add Skill OS metadata fields to package-safe catalog examples.
- Add compatibility checks for plugin metadata.
- Document how catalog plugins can describe skills, prompts, permissions, and guardrails.

Safety boundary:

- Metadata only.
- No plugin execution changes unless separately approved.

### Sprint F: Release and Governance Hardening

Goal: make future releases easier to reason about.

Possible work:

- Post-release checklist updates.
- Stable release lane documentation.
- GitHub Packages visibility review notes.
- Skipped patch handling, including the v4.0.1 superseded state.
- Release-state validation recommendations.

Safety boundary:

- Docs and verification hardening only unless explicit approval is given.

## 6. Compatibility Requirements

v4.2 work should preserve:

- Existing CLI command names and exit-code behavior unless a change is explicitly approved.
- Existing markdown skills.
- Existing workflow registry entries.
- Existing Skill OS registries and schemas unless migrations are documented.
- Zero runtime dependencies.
- Package contents and npm package identity.
- The manual npm publish workflow.

## 7. Safety Requirements

Every v4.2 sprint should keep these rules visible:

- No hidden automation.
- No external writes without explicit confirmation.
- No permission enforcement until an opt-in model is designed and approved.
- Guardrails remain advisory unless a future sprint explicitly changes that boundary.
- Dangerous operations require clear confirmation and auditability.
- Draft-only business operator templates must remain draft-only by default.
- Local validation must pass before pushing changes.

## 8. Documentation Requirements

v4.2 documentation should:

- Mark v4.2 as planned until a release-prep sprint starts.
- Keep v4.1 documented as the released Skill OS foundation.
- Explain any advisory-to-enforced transition carefully.
- Include examples that are generic and public-facing.
- Avoid private business details.
- Keep GitHub Packages visibility caveats accurate.
- Keep v4.0.1 documented as superseded and unpublished.

## 9. Validation Requirements

Minimum validation for docs-only planning:

- `npm run docs:build`
- `npm run verify`

Minimum validation for implementation sprints:

- `npm run build`
- `npm run check:build`
- `npm test`
- `npm run verify`
- `npm run docs:build`
- `npm pack --dry-run`
- Relevant read-only CLI smoke tests.

Implementation sprints should report test count, verification count, package version, npm latest, and GitHub Actions status.

## 10. Open Questions

- Should `main` move to `4.2.0-dev.0` before implementation starts?
- Should JSON output be added broadly across `skill-os` commands or only to status/validate/list?
- What is the minimum safe audit log shape for future guardrail enforcement?
- Should enforcement live only in CLI workflows, or also in plugin/catalog operations?
- Should GitHub Packages visibility be made public manually, or remain an optional authenticated mirror?
- Should v4.0.1 draft release remain indefinitely, or should maintainers document a longer-term archive policy without deleting tags?

## 11. Final Recommendation

Proceed with v4.2 as an incremental safety and usability cycle. Start with CLI inspection and planning ergonomics, then design enforcement before implementing it. Keep the project zero-runtime-dependency, validation-first, and explicit-confirmation-first.

Recommended first action: run a small v4.2 development lane safety sprint to decide whether `main` should move from `4.1.0` to `4.2.0-dev.0` before feature work begins.
